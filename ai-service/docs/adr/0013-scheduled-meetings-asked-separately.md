# ADR 0013: 會議裡約好的會議另外問一次，由程式提成行事曆活動

## Status

Accepted（2026-09-28）。依據一次性的實測（`.scratch/ai-answer-quality/meeting_times_probe.py` 與
`.scratch/local-platform-model/bakeoff/` 的 runs `*__31/32.json`）。

## Context

會後處理要在會議約了下次開會時提出行事曆活動。本機的 `qwen3:14b`（ADR 0011）在 agent 迴圈裡從來不提：臺大那段明講「臨時校務會議
定於 3 月 24 日上午召開」，6 次都漏；系統提示加了「講到下次開會要用 calendar_create_event 提出」、再加「提案前的檢查清單」都沒用。
它在 agent 裡一次要讀資料、決定提哪些案、寫會議紀錄，行事曆總是被擠掉。

同一個模型**單獨**被問「與會者在會議裡約好、之後要一起開的會議有哪些，回 JSON」時（整份逐字稿，每行帶「分:秒」）：三段會議各 3 次，
9 次全對——臺大那段每次都找到 3/24 的臨時校務會議；公司搬家那段（只有搬家日期）與臺中市政會議（防空演習、嘉年華等公告給民眾的活動）
每次都回空的。唯一的問題是時間：會議只講「上午」，它填了 `10:00`。

## Decision

- agent 跑完之後（有日曆工具、還沒超過 2 分鐘時）另外問一次，找到的會議由**程式**提成行事曆活動，不靠 agent。系統提示裡要 agent
  提下次開會的那條規則拿掉。
- 放在 agent 之後而不是之前：可以跳過 agent 已經提過的同一天活動；之前執行過的也跳過（同一個會議每次名稱寫法不同，用日期認）。
  代價是 agent 同一天提了不相干的行事曆活動時，那天約好的會議也不提；這次找到的同一天不同會議（上午籌備會、下午正式會）都提。
- 一次會後處理的 LLM 呼叫上限維持 10 次：有日曆工具時 agent 最多 9 輪，最後一次留給這個問題。
- 時間只信會議講的：模型說的「講時間的字」要真的出現在逐字稿裡，而且講了幾點（「三點」「10時」「15:00」）才用它給的時間（一小時；
  「下午三點」給成 03:00 也當下午）；否則依講到的時段（上午 9–12 點、下午 14–17 點、傍晚、晚上…），什麼都沒講就上午九點——都在
  說明裡請使用者確認。日期檢查跟待辦的期限一樣（上傳當天到一年後），錄音時間檢查跟待辦的依據時間一樣。
- 提案經過日曆工具本身（`calendar_create_event` 的參數檢查），跟模型提的一樣。
- 所有模型都這樣做，包括自有金鑰的：agent 少一輪、多一次讀整份逐字稿的呼叫。更強的模型在 agent 裡提了的話，這一步找到同一天
  的活動就跳過。
- 這個問題失敗（LLM 呼叫失敗、回覆看不懂）不影響 agent 的提案，當作沒有找到。

## Consequences

- 實測（正式流程，每段 2 次）：臺大那段 2 次都提出「臨時校務會議 2018-03-24 09:00–12:00」，附 00:14 的原句與「會議只講了上午，時間請確認」；
  另外兩段沒有誤提。每次會後處理多一次讀整份逐字稿的 LLM 呼叫（1 小時的錄音約 2.5 萬 token，本機 32k context 放得下；上傳上限約
  1 小時），多幾秒。這一次呼叫在 agent 用完 2 分鐘之後就不問，但本身不另外限時。
- 只找會議，不找其他有日期的事（搬家日、活動報名截止）；那些仍然交給 agent（待辦的期限）。
- 更強的模型可能在 agent 裡就會提；那時這一步多半只是找到同一天的活動而跳過，不會重複。
